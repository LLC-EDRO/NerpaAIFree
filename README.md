# Nerpa Template Lab

## Синхронизация движка с Nerpa

Это изолированная лаборатория генерации презентаций по пользовательскому PPTX. Парсер и рендерер находятся в `backend/vendor/presentation-agent`, состояние проектов хранится в локальных JSON-файлах. Текст и изображения слайдов анализирует Gemma 4 через локальный Ollama. Для создания новых изображений выбрана FLUX.2 [klein] 4B; её сервер пока не подключён.

В лаборатории можно одновременно разбирать и собирать до трёх проектов. Данные проектов, платежи, публичные страницы и интерфейс основного сервиса сюда не переносятся. Для проверки: `npm run sandbox`, `npm run build`, `npm test`, `npm --prefix backend run test:native`. Python-проверки запускаются в собранном Docker-образе с примонтированными тестами из `backend/vendor/presentation-agent/runtime`.

## Мягкий смысловой QA и совместный патч ИИ

Проверка содержания v7 допускает перефразирование, сокращения, отсутствие части фактов плана и неполные подписи. Неоднозначные замечания, неподтверждённые подозрения и редакторские предложения сохраняются в `reviewNotes`, не останавливая этап. Противоречие фактам блокирует только при наличии точного фрагмента написанного текста и цитаты из переданных источников. Явно бессмысленный обрывок текста и уход от темы остаются поводом для исправления. Числовое подтверждение, целостность файла и физический рендер проверяются отдельно.

ИИ может вернуть единый структурированный патч `frames` (координаты и размеры) + `fields` (текст и evidence). Это данные, не исполняемый код. Ключи ограничены редактируемыми полями слайда; шрифты, логотипы и произвольные свойства менять нельзя. Текст и геометрия сначала проверяются на копии; если патч отклонён, оба изменения отменяются. После принятия сохраняются проверка смысла и финальный PDF-контроль. При отсутствии безопасного расширения ИИ может предложить только короткий текст. Изображения используются в диагностике ремонта, а не повторяются в каждом обычном заполнении.

Точечный тест новой политики: `cd backend && npx tsx test/qa-policy-live.mts`. Обычный `npm test` не вызывает провайдера. Эти проверки не подтверждают время полного 15-слайдового цикла.

## Параллелизм и полный замер

`SLIDE_CONCURRENCY` ограничивает независимые операции ИИ над слайдами (1–15, по умолчанию 8). `PPTX_CONCURRENCY` отдельно ограничивает тяжёлые Docker-процессы (1–4, по умолчанию 2). На тестовом компьютере установлены 15 и 3: три контейнера требуют до 6 ГБ памяти Docker. После изменения переменных backend нужно перезапустить. Модель и обязательные проверки от числа воркеров не меняются.

Проверки вместимости объединяются в пакеты, сохраняя адреса ошибок каждого слайда. Смысловые проверки могут разделять общий контекст источников. Полная исходная геометрия сохраняется; сокращается только повторяемый контекст запросов. Рекомендуемая длина текста передаётся в промпт. Жёсткого `maxLength` для прозы нет: такой лимит дал обрывки фраз в реальном пилоте и был удалён.

Для нового замера, включая загрузку, план, описание, заполнение, проверки и скачивание:

```sh
cd backend
node test/performance-pilot.mjs '/absolute/template.pptx' 'Тема презентации' '/absolute/new-output-directory' 15
```

Скрипт создаёт новый проект, сохраняет исходные изображения и пишет `run.json` с этапами, токенами, полным временем и `withinTarget`. Каталог должен быть новым. Цель — 300 секунд, но она не является гарантией для произвольного шаблона или локальной модели. Возобновление проекта не считается полным замером. Диагностика времени работы и ожидания native-процессов сохраняется в `performance/*.json` внутри каталога соответствующего этапа.

Изолированный прототип генерации презентаций по пользовательскому PPTX. Рабочий `nerpa-service` не участвует в запуске. Базы данных, аккаунтов, оплаты и Redis здесь нет. Состояние, исходники, ответы моделей и результаты хранятся в `backend/data/`.

## Настройки моделей

Текст, планирование, анализ изображений слайдов и проверка содержания направляются только в локальный Ollama. Выбрана мультимодальная `gemma4:12b`. Установите её командой `ollama pull gemma4:12b`; затем откройте «Настройки моделей», загрузите доступные модели и сохраните выбор для текста и анализа слайдов.

`backend/.env` содержит адрес Ollama и имена моделей:

```env
LOCAL_MODEL_URL=http://127.0.0.1:11434
LOCAL_TEXT_MODEL=gemma4:12b
LOCAL_VISION_MODEL=gemma4:12b
LOCAL_IMAGE_MODEL=FLUX.2-klein-4B
```

Выбор для новых экспериментов сохраняется в `backend/data/model-settings.json`. Старые настройки удалённого провайдера не активируются. Веб-поиск выключен; факты и ссылки вводятся в материалы проекта. Генерация новых картинок пока не подключена: имя FLUX.2 [klein] в `.env` не устанавливает веса и не создаёт сервер изображений. Исходные изображения можно сохранить или заменить загруженным файлом.

```sh

```

Интерфейс: http://127.0.0.1:5174. Backend: http://127.0.0.1:4100. Эти порты отделены от рабочего сервиса. Приложение слушает только loopback.

Для установки на другом компьютере:

```sh

cp backend/.env.example backend/.env
# Установите локальную модель: ollama pull gemma4:12b

```

`npm run sandbox` собирает независимый образ из Python/LibreOffice. `npm run sandbox:local` — ускоренная сборка поверх уже установленного `nerpa-pptx-sandbox:1`; исходный образ не меняется. При изменении Python-кода пересоберите образ. `npm run build` собирает backend и frontend; затем `npm --prefix backend start` запускает собранное приложение на порту 4100, включая frontend.

## Сценарий

1. Загрузите PPTX до 40 МБ. Обработчик проверяет архив, извлекает объекты, читает шрифты и строит превью. Недоступные для безопасного заполнения макеты остаются видны с причиной.
2. Введите тему, число итоговых слайдов (1–20, включая титульный), факты и требования. Модель предложит план с конкретными исходными макетами.
3. Отредактируйте заголовки, смысл, порядок и выбор макетов. Один макет можно использовать несколько раз. Нажмите «Утвердить и проанализировать».
4. Сервер **физически собирает выбранные слайды в отдельный PPTX**. Затем повторно разбирает и рендерит именно его. Модель получает по одному изображению каждого собранного слайда, точные поля парсера и контекст всего утверждённого плана. Так анализируется весь собранный макет без попытки заставить модель самостоятельно читать ZIP/XML.
5. Посмотрите или скачайте `template.json` и собранный PPTX. В JSON есть точные координаты, размеры, стили, ключи, исходное происхождение, связи смысловых групп, назначение полей и правила замены.
6. Нажмите «Создать презентацию». Для каждого слайда выполняются заполнение, проверка ключей/данных, физическое измерение текста и отдельная проверка смысла моделью. Исправляются только проблемные поля, максимум шесть кандидатов на слайд за проход. Допустим ответ модели только с исправленными полями; остальные значения сервер сохраняет сам. Успешные слайды сохраняются и снова проходят физическую проверку при использовании кэша.
7. После экспорта проверяется PDF-рендер. Его ошибки автоматически возвращаются в исправление соответствующих полей: до трёх повторных сборок. Причины, отклонённые значения и точное содержимое сбойного прохода сохраняются в `output-rN/repair-state.json`; при повторном запуске они не теряются. Идентичный отклонённый результат не экспортируется повторно. Тайм-аут финального обработчика допускает один автоматический повтор без новых запросов к модели. PPTX/PDF и изображения доступны через API только после успешной проверки; презентация остаётся редактируемой.

Исправимые ошибки обрабатываются внутри одной генерации без кнопки «Повторить». Если автоматические попытки исчерпаны, диагностический JSON и контрольные точки остаются доступны. Если утверждённый макет физически несовместим с содержанием, вернитесь к плану и выберите другой. После изменения плана старое описание не используется. Остановка прерывает запрос модели; текущий изолированный разбор PPTX завершается перед остановкой следующего шага. После перезапуска backend незавершённые задания помечаются прерванными, а не продолжают висеть.

## Что перенесено и что изменено

Из рабочего backend скопированы изолированный Python-парсер PPTX, измеритель native-текста, OOXML-заполнитель, проверка PDF и защищённый Docker-протокол. Они находятся в `backend/vendor/presentation-agent`; прототип не импортирует исходники из рабочего проекта.

В тестовой копии добавлена сборка выбранных слайдов до анализа. Парсер читает порядок слайдов по relationships, а не по имени `slideN.xml`, и находит диаграммы по content type: это необходимо для повторного разбора собранного и экспортированного PPTX. При заполнении сохраняются исходные фото и декор, а неизменённые поля не переписываются — сохраняется их rich text. Автоматическая перестановка объектов и уменьшение шрифта отключены.

JSON здесь — отдельный контракт native-шаблона `nerpa-native-template/1`. Геометрия берётся из PPTX, модель добавляет смысловой слой. Произвольный PPTX не преобразуется в ограниченный набор встроенных компоновок Nerpa. Это сохраняет пользовательское оформление и позволяет проверить гипотезу описания перед заполнением.

## Настройки моделей и приватные файлы

Все запросы анализа и заполнения отправляются в локальный Ollama по адресу из `LOCAL_MODEL_URL`. Секреты облачных провайдеров не нужны. Не добавляйте пользовательские презентации, результаты генерации и локальные веса моделей в Git.

Локальные шрифты лежат в `backend/fonts`; также используются установленные шрифты macOS. На другом компьютере установите нужные шрифты. Подстановки отражаются в `analysis.json` (`fontReport`, `fontSubstitutions`). Docker работает без сети, без прав root, с файлами ввода только для чтения и ограниченными ресурсами.

## Файлы эксперимента

`backend/data/projects/<id>/`:

- `project.json` — состояние, план, краткая история этапов;
- `source/` — исходный PPTX, parser/analysis/frames JSON и превью;
- `plan-rN.json` — версия плана;
- `assembled-rN/` — собранный PPTX, его разбор и промежуточная семантика;
- `template-rN.json` — единый контракт шаблона;
- `output-rN/copy-I.json` — заполнение, ошибки вместимости и отклонённые значения по слайдам;
- `filled-rN.json` — точные команды заполнения;
- `output-rN/` — PPTX/PDF/PNG и проверка рендеринга;
- `llm/` — ответы моделей и расход токенов, без ключей;
- `research.json` — найденные факты, ссылки, запросы, время и идентификатор задания;
- `last-error.json` — последняя ошибка.

## Проверки

```sh
npm run build
npm test
npm --prefix backend run test:native
```

Native acceptance использует `fixtures/cobalt-editorial.pptx`: собирает титульный слайд и две копии одного макета диаграммы, заполняет их разными значениями, проверяет fit и PDF. Результат в `backend/data/native-acceptance/`. Сетевые LLM-вызовы этот тест не делает. Обычные unit-тесты проверяют сопоставление ключей, подтверждение чисел цитатами, обязательные поля и границы sandbox-протокола.

Подробности выполненных проверок и обнаруженные ограничения: `VALIDATION.md`. Пример полного живого сценария с синтетическими данными: `examples/pilot/`.

## Границы эксперимента

Это прототип для локальной проверки гипотезы, не доказательство надёжности на любых презентациях. Сохраняются исходные фотографии и декоративные изображения; их автоматическая генерация/замена не включена. Поддерживаемые диаграммы остаются редактируемыми, число категорий и рядов сохраняется. Для диаграммы нужны реальные данные в материалах. Текст внутри фотографий не превращается в редактируемые поля. Сложный SmartArt, неподдерживаемая геометрия и проблемные шрифты могут сделать макет недоступным.

Числа проверяются по точным цитатам и дополнительным смысловым запросом, но содержание всё равно требует просмотра человеком. Проверки вместимости и PDF не гарантируют одинаковый рендер в каждой версии PowerPoint. Интерфейс хранит файлы локально, однако материалы выбранных слайдов передаются настроенным LLM при генерации.

## Автоматическое восстановление и границы проверки

- Предварительный fit и проверка реального PDF — разные ступени. Последняя проверяет видимые глифы, выход за страницу/поле, пересечения, перекрытия и шрифты. Ошибка последней ступени снимает `passed` у соответствующей контрольной точки.
- Для рамки за краем страницы требуется вместимость каждой явной строки в видимую ширину: ранний перенос измерителя больше не скрывает обрезание при рендеринге. Геометрия и шрифты исходного PPTX не меняются.
- Исправление не отменяет проверку исходных материалов и редакторскую проверку; отсутствие числа не разрешает придумать его или утверждать отсутствие самого явления.
- Журнал привязан к ревизии, SHA макета, плану и фактам; ошибка применяется только к совпадающему содержимому. При отмене или ошибке результат не публикуется.
- Не гарантируется заполнение произвольного несовместимого PPTX. Отсутствующие данные для обязательной диаграммы, недоступные шрифты, неподдерживаемая структура и физически невместимый обязательный смысл требуют изменения условий. Утверждённые макеты автоматически не подменяются.
- Автоповтор инфраструктуры добавлен для тайм-аута финального экспорта; ошибки локальной модели и конфигурации по-прежнему возвращают отдельную диагностику. Автовозобновление задания после перезапуска сервера не включено: повтор запуска восстанавливает сохранённое состояние исправлений.

## Расход токенов

На каждой вкладке отображается таблица Input/Output по этапам, а рядом со скачиванием результата — итог за весь проект. Суммы вычисляются из сохранённых ответов в `llm/*.json`, включая все ревизии, повторные попытки и редакторские проверки. Существующие проекты получают статистику без новой генерации. Повторное открытие и скачивание не увеличивают счётчики.

Используются `prompt_tokens` / `completion_tokens` для Chat Completions и `input_tokens` / `output_tokens` для Responses. Детализация cache/reasoning уже входит в эти значения и не прибавляется повторно. Если в сохранённом ответе нет счётчиков, интерфейс показывает «Нет данных» или нижнюю границу «≥». Запрос, при обрыве которого ответ провайдера вообще не был получен и сохранён, нельзя восстановить из этих журналов; это статистика полученных ответов, не сверка биллинга провайдера.


## Факты и обязательные метрики

Редактор проверяет написанные утверждения, а не полноту переноса плана. Пропуск отдельного показателя, короткое пояснение разделителя и понятные сокращения не блокируют экспорт. Замечания о недостающих деталях и стилистике сохраняются как неблокирующие заметки. Исправление запускают фактическое противоречие, неподтверждённое конкретное утверждение или уход слайда от темы. Старые редакторские требования из контрольных точек сбрасываются при обновлении политики, но история физических переполнений сохраняется.

Обязательные метрики заполняются числом из материалов пользователя или сохранённого поискового факта. Пустота, тире, «Н/Д» и «нет данных» не считаются готовой метрикой. Если нужный показатель отсутствует, модель может выбрать другой подтверждённый показатель в рамках темы и согласованно изменить его подпись, единицы и период. Все поля одной смысловой группы участвуют в исправлении; другие группы сохраняются.

Для качественного пояснения допустимы устойчивые знания модели. Числовая статистика требует evidence и проверки смысла (предмет, выборка, период, единицы); уверенность модели сама по себе не является источником. Без достаточных фактов презентация не должна содержать выдуманных чисел. Поскольку веб-поиск выключен, источником чисел остаются материалы пользователя.

## Изображения слайдов

Система определяет крупные тематические изображения; иконки, логотипы и декор сохраняются. В панели можно оставить оригинал или загрузить PNG/JPEG/WebP до 24 МБ. Модель FLUX.2 [klein] 4B указана в конфигурации для будущего локального подключения, но сейчас генерация новых изображений выключена в backend. Выбор «Создать» недоступен; сервис не отправляет запросы к удалённому генератору изображений.

## Автоматическая адаптация плана после смены макетов

При сохранении изменений AI адаптирует заголовки и содержание затронутых слайдов к выбранным макетам: учитывает число блоков, таблицы, графики, вместимость полей, исходные изображения и общий план. Выбранные макеты, порядок, идентификаторы и число слайдов сохраняются сервером. Статистика берётся из материалов и сохранённых источников; образцы шаблона не считаются фактами.

Кнопка «Утвердить и проанализировать» сохраняет правки, запускает адаптацию и затем сборку/описание одной серверной задачей. Повторное подтверждение адаптированного плана не требуется. Перезагрузка страницы не прерывает задачу. Кнопка «Сохранить изменения» запускает только адаптацию плана. При неизменном плане повторных AI-запросов адаптации нет; завершённые пакеты кэшируются для продолжения после сбоя. План публикуется после всех пакетов и получает новую ревизию; старое описание и заполнение инвалидируются. Токены и стоимость адаптации входят в «Генерация плана».

### Крайнее восстановление отдельного макета

После неудачных локальных правок текста и рамок AI может предложить новую компоновку только проблемного слайда. Для обычных редактируемых слайдов с непроверяемыми исходными рамками этот путь доступен сразу: исходный PPTX должен успешно пройти разбор пакета. Повторный конфликт в итоговом PDF также переводит слайд на восстановление вместо бесконечного сокращения текста.

Модель возвращает декларативный JSON, не исполняемый код. Сервер сохраняет фон, защищённые элементы, исходные изображения, редактируемые диаграммы и число колонок таблиц; новые таблицы имеют отдельные заголовки и строки данных. Доступны только установленные шрифты и палитра исходного шаблона. Геометрия проверяется на границы и пересечения, затем выполняются измерение текста, проверка содержания и рендер. После полной перекомпоновки последующие правки по возможности ограничиваются ошибочными текстовыми рамками. Успешные соседние блоки сохраняются.

Журнал `output-rN/rebuild-I.json` содержит предложения и причины отказов. В результате `rebuiltSlides` и интерфейсе показываются номера изменённых слайдов и объяснения. Лимиты попыток сохраняются: повреждённые пакеты и неподдерживаемые объекты не объявляются успешно восстановленными. Поддержка любых сочетаний SmartArt, OLE и сложных групп этим механизмом не гарантируется.

Стресс-корпус из десяти новых искусственно проблемных макетов: `fixtures/stress-2026-09-24/`. Исходный шаблон создан отдельно, без использования ранее загруженных пользовательских презентаций. Цифры учебного кейса вымышлены и явно обозначены; веб-поиск и генерация изображений в этом пилоте выключены.


## Текущая модель

Активная локальная модель: `gemma4:12b` для текста и анализа слайдов. Адрес и имена моделей задаются в `backend/.env`; наличие модели проверяется через Ollama. Веб-поиск и генерация новых изображений пока недоступны.
